## 1. この計画書について

設計書 9 章の実装指示は 11 段階で、1 段階が大きい（たとえば段階 2 は画像処理エンジンの全部）。この計画書は、それを機能 1 つごとのステップに分け、作る順番と、ステップごとの確かめ方を決める。

- 仕様は設計書が正である。この計画書が決めるのは順番・区切り・確かめ方だけで、仕様は書かない。
- 段階の番号は設計書 9 章と同じにしてある。「2-4」は、段階 2（エンジン）の 4 番目のステップを指す。
- 1 ステップは、終えた時点でビルドとテストが通り、そのステップだけで動作を確かめられる大きさにしてある。
- テストの番号（E・W・V・R・T）は設計書 6 章のもの。「追加」は、設計書に番号は無いが、そのステップだけで動作を確かめるために足すテストである。

### 1.1 計画を作った時点の状態

- 段階 1（基準ファイルの作成）は終わっている（コミット `67473cc`）。
- `dotnet test CoverCropper.slnx` は 62 件すべて成功する（CoverCropper の既存テスト 53 件と、`BaselineRegressionTests` の 9 件）。.NET SDK は 10.0.402。
- webDeza のコードはまだ無い（`WebDeza/doc/` に設計書とこの計画書があるだけ）。

## 2. 進め方

### 2.1 1 ステップの流れ

1. ステップの番号を指定して、Claude Code に実装を指示する（例: 「2-2 を実装して」）。小さいステップは「2-5 と 2-6」のようにまとめて指示してもよい。
2. Claude Code は、設計書の該当する所を読んで、そのステップの「作るもの・変えるもの」を実装し、「確かめること」のテストを足す。
3. `dotnet build CoverCropper.slnx` と `dotnet test CoverCropper.slnx` を実行する。
4. この計画書の「状態」を「済」に直し（段階のステップがすべて済んだら、3 章の表も直す）、結果を報告する。手動で確かめることがあれば、その手順も報告に書く。
5. 結果を人が確かめる。コミットは指示があったときに行う（1 ステップの変更は、1 回のコミットにまとめられる大きさにしてある）。

### 2.2 ステップを終える条件

- ビルドが成功し、テストがすべて成功する。
- `CoverCropper.Tests` のファイルを書き換えていない（設計書 1.4）。
- 「確かめること」に書いたテストがあり、成功している。
- 「手動」と書いた確認は、手順を報告に書いてある（画面の操作が要るため、人が確かめる）。

### 2.3 決まり

- 段階もステップも番号順に進める。後のステップは、前のステップで作ったものを使う。
- そのステップに書いていない機能を先に作り込まない。ただし、後で作り直しにならないための形（各段階の「注意」に書いたもの）は先に取っておく。
- 設計書のとおりに作れない所や、設計書とこの計画書の食い違いに気づいたら、実装を止めて相談する。決まったら設計書か計画書を直してから進める。
- ステップを分けたほうがよい・まとめたほうがよいと分かったら、この計画書を直す。

| 状態 | 未 / 済 |

| `ExportEncoder` のテスト（E30） | 段階 2 | 2-16 と 3-4 の 2 回 | 段階 2 の時点では実際の形式が無いため、偽のエンコーダーで確かめておき、段階 3 で実際の JPEG・PNG でも確かめる |
| `AppModules.Register` の引数 | 形式・フィルター・道具・プリセットの 4 つ | 段階を追って増やす | 道具とプリセットの仕組みが、後のステップでできるため。最後は設計書 5.6 の形になる |
